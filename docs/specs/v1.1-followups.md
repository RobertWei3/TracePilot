# TracePilot V1.1 — 补充 Spec

本文是 [`REPORT.md`](../../REPORT.md) 中 **Cuts** 一节的后续实现规格。每一项（T1–T5）都是独立的工作单元，可以在单独的会话中完成，互不依赖（T4 与 T5 有一个可选的衔接点，见各自说明）。

代码位置均以 `main` 分支 `7fd0150` 为准。开始一项之前，先确认引用的行号仍然成立。

## 通用规则（每一项都适用）

- **先红后绿。** 先写一个能复现问题的失败测试，再修。测试放在 `tests/` 下已有的对应文件里，复用 `tests/helpers/`（`app.ts` 启动 DemoBank，`scripted.ts` 驱动无模型的 discovery）。
- **不破坏现有承诺。** 以下几条由 `tests/boundaries.test.ts` 等测试保证，任何改动都不能削弱它们：
  - replay 不调用模型（`modelCalls: 0`），也不能 import discovery 或 LLM SDK。
  - compiler 只 import `contracts/`。
  - 只有 `browser/` 碰 Playwright。
  - 持久化记录和截图里不出现输入值、凭据。
- **改 schema 要同步。** 改了 `src/contracts/` 里的 zod schema，就要确认 `schemas.ts` 生成的 JSON Schema、`tests/fixtures/` 和 `evidence/` 里的已有文件仍然能通过校验。新增字段优先设计成可选或带默认值，避免让旧的 capability 和 result 文件失效。
- **完成标准：** `npm run typecheck` 和 `npm test` 全绿。如果这一项让 `REPORT.md` 的 Cuts 中某一条不再成立，就同步删除或改写那一条。
- 每一项单独开分支、单独提 PR。

## 建议顺序

| 顺序 | 项目 | 规模 | 类型 |
| --- | --- | --- | --- |
| 1 | T1 应用不可达时 replay 返回 `LOAD_FAILED` | 小 | Bug |
| 2 | T2 审批 diff 只列出被写入的表单字段 | 小 | Bug |
| 3 | T3 建立 CI | 小 | 基础设施 |
| 4 | T4 replay 时比对 surface 指纹 | 中 | 功能 |
| 5 | T5 `inspect` 与 `diff` 命令 | 中 | 功能 |

建议先做 T3，或者至少在 T1、T2 合并之前做完 T3，这样后面每个 PR 都有 CI 把关。

## T1 — 应用不可达时 replay 应返回 `LOAD_FAILED`，而不是抛异常

### 现状（已确认）

`ReplayExecutor.run()`（`src/replay/executor.ts:120`）在进入步骤循环之前，会先调用 `surface.ensureSession()`。`ensureSession`（`src/browser/driver.ts:322`）里的 `this.navigate(loginUrl)` 最终调用 `page.goto`。如果应用连不上，`page.goto` 会以 Playwright 的网络错误 reject（例如 `net::ERR_CONNECTION_REFUSED`）。

这个错误没有被包装。它冒泡到 `handleThrow`（`src/replay/executor.ts:817`），而 `handleThrow` 只识别 `Terminal`、`Escalate`、`SafetyViolation` 和 `UnresolvableValue`，其他异常一律原样抛出，导致 CLI 崩溃，不会产出 `result.json`。

步骤内的加载已经由 `withLoadRecovery`（`src/replay/executor.ts:628`）转成了 `LOAD_FAILED`。所以只有**第一步之前**的这段路径漏掉了。

### 要求

1. 在建立会话阶段，导航失败（网络错误或超时）时，run 正常结束：
   - `outcome: "failure"`，`reasonCode: "LOAD_FAILED"`。
   - `expected` 写 "the login page to load"，`observed` 写错误名或错误类别。**不要**写完整的错误信息，因为里面可能带 URL 参数。
   - 写出 `result.json`，CLI 退出码非 0，和其他 failure 一致。
2. 会话建立阶段的导航失败，也应该消耗 `policy.recovery.reloads` 的配额，重试一次之后再失败，行为和步骤内的加载保持一致。复用 `withLoadRecovery` 的思路，但要注意它需要一个 `step` 参数；这里没有 step，需要相应调整（比如把 `step` 设为可选）。
3. `handleThrow` 增加一个兜底分支：未知异常一律转成 `outcome: "failure"`，`reasonCode` 用现有的、最接近的错误码；没有合适的就新增一个 `INTERNAL_ERROR`，并加进 `src/contracts/result.ts` 的错误码列表。同时记录一个事件，字段只包含 `e.name`。这样以后同类的漏网异常也不会让 CLI 崩溃、丢掉 result。
4. discovery 的启动路径（`src/discovery/executor.ts`）要检查是否存在同样的问题。如果有，按同样的方式修。

### 验收

- 新测试：在 `tests/replay.test.ts` 中，用一个没有服务监听的端口（例如先拿到一个空闲端口再关掉）作为 `baseUrl` 跑 oracle capability（`tests/fixtures/update_mailing_address.v1.json`）。断言返回的 result 满足 `outcome === "failure"`、`reasonCode === "LOAD_FAILED"`、`modelCalls === 0`，并且 run 目录下存在 `result.json`。
- 删除 `REPORT.md` Cuts 中 "An unreachable application makes replay throw" 这一条。

## T2 — 审批 diff 只列出本次写入的表单字段

### 现状（已确认）

discovery 每做一次 fill，都会推入 `pendingFills`（`src/discovery/executor.ts:570`）。审批时，`doApproval`（`src/discovery/executor.ts:718`）把**全部** `pendingFills` 都做成 diff，并据此计算 digest。

搜索页上填写的 `member_id` 也在 `pendingFills` 里，所以审批 diff 中出现了 `textbox near "Member ID or last name" in "Member search"`。这一条会经由 trace 编译进 capability 的 `diffFields`，见 `evidence/03-capability/demobank.update_mailing_address.v1.json` 第 634 行附近。而手写的 oracle（`tests/fixtures/update_mailing_address.v1.json`）只列出了地址字段。

### 设计

观察到的元素已经带有 `submitTarget: { method, pathname } | null`（`src/browser/observe.ts:118`, `:350`），它给出的是这个元素所在表单的提交目标。`classifyEffect(policy, submitTarget)` 已经被用来判断一个点击是不是写操作（`src/discovery/executor.ts:495`）。

1. `pendingFills` 中每一项增加 `submitTarget` 字段，在 `doFill` 时从 `el.submitTarget` 取值。
2. `doApproval` 构造 diff 时，只保留 `classifyEffect(policy, f.submitTarget) === "consequential"` 的字段。digest 只基于这些字段计算。
3. 如果过滤后一个字段都不剩，就拒绝这次审批，提示 "no field that this write would submit has been changed"。原来的那条拒绝文案同样要覆盖这种情况。
4. 发生 consequential click 之后，计算 `writtenInputs`（`src/discovery/executor.ts:529`）时也应该只用过滤后的字段，而不是全部 `pendingFills`。目前靠 `from.includes(<input:…>)` 间接排除了搜索框，要确认过滤之后这个间接排除仍然正确，或者已经不再需要。
5. replay 侧（`src/replay/executor.ts:370`）直接使用 capability 里的 `diffFields`，不需要改，但要确认编译出的 capability 不再包含搜索框。

### 验收

- 在 `tests/discovery-loop.test.ts`（或 `tests/handoff.test.ts`，看审批相关测试放在哪里）中，用脚本化 discovery 走完 "搜索 → 编辑 → 审批 → 提交"。断言审批请求的 `diffFields` 只包含编辑表单里的字段，不包含搜索框。
- 用 `tests/fixtures/update_mailing_address.trace.json` 编译一次，确认 `diffFields` 的标签集合与 oracle 一致。如果这个 fixture 本身就是用旧行为录的，就重新生成或手动修正，并在 PR 里说明。
- 删除 `REPORT.md` Cuts 中 "The approval diff lists the search box as a pending change" 这一条。**`evidence/` 下的已有文件不要改**，它们是历史记录。

## T3 — 建立 CI

### 现状

仓库里没有 `.github/workflows/`。`tests/discovery-live.test.ts` 在没有 `DEEPSEEK_API_KEY` 或 `ANTHROPIC_API_KEY` 时会自动 skip（`tests/discovery-live.test.ts:25-29`），并且按设计它不应该卡 CI。

### 要求

1. 新增 `.github/workflows/ci.yml`，在 push 到 `main` 和每个 pull request 时触发：
   - `actions/setup-node`，Node 24，开启 npm cache。
   - `npm ci`
   - `npx playwright install --with-deps chromium`，并缓存 `~/.cache/ms-playwright`，key 用 Playwright 的版本号。
   - `npm run typecheck`
   - `npm test`。浏览器测试需要 headless，确认测试 helpers 在 CI 下默认 headless；如果不是，就通过环境变量（例如 `CI=true`）切换，**不要**改变本地默认行为。
   - 这个 job **不注入**任何模型 key，所以 live 测试一定会被 skip。
2. 新增 `.github/workflows/live.yml`，只用 `workflow_dispatch` 和每周一次的 `schedule` 触发，注入 secret `DEEPSEEK_API_KEY`，只跑 `discovery-live.test.ts`。失败时把 `runs/` 作为 artifact 上传。上传前确认 `runs/` 里没有凭据：按 REPORT 的说法，记录已经过脱敏，但要在 PR 里说明你检查过。
3. 第一次在 CI 上跑通之前，可能会暴露对本地环境的隐式依赖，比如固定端口、`profileDir` 或时区。这类问题要修代码，不要在 CI 里打补丁绕过去。

### 验收

- PR 上的 CI 是绿的，并且日志里能看到 live 测试被 skip。
- `live.yml` 可以手动触发；仓库里配置 secret 由仓库 owner 来做，PR 描述里要写明需要哪个 secret。
- `REPORT.md` 里 "the live smoke test does not gate CI" 这句保留，因为它仍然成立，只是现在有 CI 了。

## T4 — replay 时比对 surface 指纹，提前发现漂移

### 现状

- discovery 为每一步记录 `surfaceFingerprint = fingerprint(step.target)`（`src/discovery/executor.ts:943`）。`fingerprint()`（`src/browser/descriptor.ts:68`）是对 `role`、`tagName`、`accessibleName`、`labelText`、`scope.containerName` 计算的哈希。
- 编译器把它原样带进 capability（`src/compiler/compile.ts:155`）。整条 run 还有一个 `appFingerprint`。
- replay 目前**完全不读**这两个值。唯一的漂移信号是定位优先级跌到第 1 级以下（`attempt.rank > 1`，`src/replay/executor.ts:339`），结果写在 `result.drift.stepsResolvedBelowRank1` 和 `score` 里（`:1027`）。

这有一个盲区：按钮被改名之后，如果 label 或 text 那一级的定位仍然在第 1 级命中，或者 structural 定位恰好命中了错的元素，现在都不会报告漂移。

### 设计

1. `browser/` 提供一个方法，比如 `surface.describeResolved(locator)`，给已解析的元素现场构造一个 descriptor，复用 `observe.ts` 里构造 descriptor 的同一套逻辑。然后对它调用同一个 `fingerprint()`。**关键是两边必须用同一套字段计算**，否则每一步都会被误报为不一致。
   - 输入值的标签化必须和 discovery 时一致。descriptor 中的 `<input:name>` 标签在 replay 时会被替换回当前值，所以比较之前要把当前值重新标签化，或者两边都在标签化之后的形式上计算。实现时需要先读清楚 `observe.ts` 和 `descriptor.ts` 是怎么处理的，再决定。
2. replay 中，每一步只要 `step.surfaceFingerprint` 存在且目标解析成功，就计算实际指纹并比较：
   - 一致：什么都不做。
   - 不一致：记录事件 `{ type: "fingerprint_mismatch", stepId, expected, observed }`，只包含哈希，不包含 descriptor 文本。这一步**照常继续**，指纹不一致只是警告，不是失败。
3. `ExecutionResult.drift` 新增 `fingerprintMismatches: string[]`（stepId 列表），必须是可选或带默认值。`score` 的计算方式改为把两类漂移步骤取并集后除以总步数。在 `src/contracts/result.ts` 的注释里写清楚 score 的定义。
4. `appFingerprint` 这次**不比较**。它是根据全部步骤指纹计算的，任何一步变化都会导致它不同，信息量不超过逐步比较。在代码注释里写明这一点就可以。
5. CLI 的 `printResult` 在出现不一致的步骤时打印一行摘要。

### 验收

- 测试 1：在 DemoBank 未改动的情况下回放 oracle capability，断言 `fingerprintMismatches` 为空。这一条用来防止误报，最重要。
- 测试 2：复用 evidence 08 的思路，构造一个 capability：把某一步的 `surfaceFingerprint` 改成另一个值，或者用 DemoBank 已有的改名手段。如果没有现成手段，就新增一个 `/_admin` 场景，比如 `relabel_button`。断言这一步出现在 `fingerprintMismatches` 中，并且 run 仍然是 `success`。
- 更新 `REPORT.md` Cuts 中 "Fingerprints are recorded, not compared" 这一条，改为说明现在是逐步比较但只做警告，`appFingerprint` 仍然不参与比较。

## T5 — `inspect` 与 `diff` 命令

### 现状

CLI（`src/cli/tracepilot.ts`）只有 `discover`、`compile`、`replay` 三个子命令。要看一个 capability，只能直接读 JSON。capability 被重新发现后会编译成新版本，但没有工具对比新旧版本。

### 要求

纯读取命令，不启动浏览器，不调用模型。逻辑放在新模块 `src/inspect/`，只依赖 `contracts/`。在 `tests/boundaries.test.ts` 里加一条规则来固定这个依赖约束。CLI 只负责参数解析和输出。

1. `tp inspect --capability <file>`，打印：
   - id、版本、`status`（例如 `needs_review`）、provenance（源 runId、模型、作者）、origin。
   - inputs（标出 optional）和 outputs（pattern、来源）。
   - 步骤表：序号、phase、action、effect、descriptor 摘要（复用或参照 `summarize`）、precondition、使用的 value 引用、checks 数量。consequential 步骤和 approval_gate 要醒目标出。
   - 业务结果识别器列表。
   - 支持 `--json`，输出结构化摘要，供以后的 dashboard 使用。
2. `tp diff <a.json> <b.json>`：
   - 头部：比较 id 和版本。如果 `capabilityId` 不同就报错退出。
   - 步骤对齐：先看 capability 里的步骤有没有稳定的 `stepId`（编译器是怎么生成的？），据此决定按 `stepId` 还是按序号对齐。对齐方式要在代码注释中说明理由。如果两者都不可靠，就用 `(phase, action, descriptor.role, descriptor.accessibleName)` 做序列对齐（LCS）。
   - 对每个对齐的步骤，报告 descriptor、precondition、checks、`surfaceFingerprint` 的变化；同时列出新增和删除的步骤。
   - inputs、outputs、识别器的增删。
   - 退出码：没有差异时为 0，有差异时为 1（和 `diff(1)` 一致）。
3. 与 T4 的衔接（可选）：T4 产出的 `fingerprintMismatches` 可以引导用户重新发现并编译新版本，再用 `diff` 查看变化。这次不需要自动化这个流程。

### 验收

- `tests/inspect.test.ts`：对 oracle fixture 调用 inspect，断言结构化摘要的关键字段（步骤数、写操作步骤、outputs）。对 oracle 和 `evidence/03-capability/…v1.json` 调用 diff，断言能识别出步骤数差异，并且不会抛异常。
- README 的 Quickstart 补上这两个命令的用法。从 `REPORT.md` 的 Cuts 中删掉 "inspect" 和 "version diffing"，"dashboard" 和 "deployment" 保留。

## 暂不纳入本轮（Backlog）

这些是 Cuts 中剩下的项。原因是它们要么需要真实的第二个场景来验证，要么是没有反例驱动的启发式改动。真的出现需求时，再按本文格式补写各自的 spec。

- **提示词缓存**（`src/discovery/model.ts`）：需要先确认 DeepSeek 的 Anthropic 兼容接口是否支持 `cache_control`。这只能降低成本，不能降低调用次数的波动。
- **模板拆分只按逗号**（`splitOnOptional`，`src/compiler/compile.ts:286`）：等出现非列表形状的文本反例再做。
- **少于 3 个字符的值不打标签**（`INPUT_TAG_MIN_LENGTH`，`src/safety/redact.ts:25`）：方向是按字段整体等值替换，而不是降低全局门槛。
- **业务结果只从源运行学**：方向是把 replay 中人工确认过的拒绝作为新识别器的录入入口。replay 本身仍然不能调用模型。
- **agent 持有控制权期间的人工干扰检测**：方向是复用 handoff 的页面内 recorder。
- **多租户 overrides、桌面端 surface、dashboard、部署**：没有真实的第二个目标之前不做。
